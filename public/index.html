Neural Net

A multilayer perceptron learns this kitchen's prep times while the shift runs: learned item and station embeddings, two SiLU hidden layers, trained online with AdamW on mini-batches from a replay buffer. Every finished dish labels itself from the kitchen's timestamps. Edges are the real weights at this moment of the shift.

shadow mode

Model releases · every 3 weeks

The network keeps training on every finished dish, every day. Every 21 days it is scored against the model in production on the last three days of dishes, and replaces it automatically only if its error is lower. The model in production sets the fire scheduler's prep-time starting point at the start of each shift.

    AI agent

    Every five finished dishes the agent reads the network's recent errors and proposes changes to it: the learning rate, the output bias, or a correction for one dish. With an OpenRouter key the proposal comes from that model; without one, a rule agent proposes. Either way the server applies a change only if it lowers error on the newest dishes, which the proposal was not built from.

      How it connects

      • Kitchen → each finished dish on the Order Line is one training example: the item and its real prep seconds.
      • Network → predicts each dish before learning from it (prequential evaluation), then takes one AdamW step on that dish plus replayed recent dishes.
      • Decision → in shadow mode the fire plan still uses the measured estimators. The network should be promoted only if it beats them on the replay benchmark.
      • AI agent → between dishes, the OpenRouter model (or the rule agent) proposes changes to the network's learning rate and biases. The server clamps them, tries them on a copy, and keeps only changes that lower error on held-out dishes. Every change is logged with its reason.

      Same shift, five policies

      Every policy sees the identical tickets, prep durations and courier arrivals. Only the firing decision changes.

      Not another inventory tracker

      Inventory tools, invoice reconciliation and bookkeeping dashboards already exist, and DoorDash ships parts of them. The crowded part of the problem is knowing things. The open part is deciding: at 7:12pm, with three stations backed up and a courier who may be four minutes out, do you start the burger now or hold it?

      Fireline is a tablet agent for the pass that answers that question per ticket, shows the arithmetic behind each answer, and keeps a measured record of whether the calls were good.

      What it decides

      One action per ticket: fire now or fire at t. Cost is seconds of food sitting plus five times seconds of courier waiting. The five is an assumption, printed on screen, and changing it changes the plan.

      What it learns

      • Prep time per menu item: a prior from the menu (median and spread), updated online from real station service times.
      • Courier bias: an exponential moving average of “arrived minus promised”, so a late market shifts the firing plan within a few tickets.
      • Queue delay: the live backlog on the critical station is added to the forecast before the cost comparison.

      Designed for the line, not for a demo

      Kitchen staff are wearing gloves and reading the board from three feet away. So: tap targets are 48–64px, a ticket opens with one tap, nothing important is hover-only, the playback controls sit in the bottom bar within reach, body text is 13–16px, focus is visible and trapped inside the drawer, and Escape closes it. No gestures, no long-press, no drag.

      What it cannot do — say this to judges

      • It does not model station changeovers, staff breaks or an item being dropped. Prep times are learned from a shift that is already happening.
      • Cold start is real: with zero observations it believes the menu. The Cold start shift shows exactly how much that costs.
      • Courier ETAs are noisy, and forty percent of tickets can arrive with no courier assigned at all. The agent plans against a distribution, not a fact.
      • Weights are a policy choice, not a discovered truth. The benchmark shows the trade, not a single “correct” answer.
      • No LLM is in the decision path. A model is optional only to rewrite the measured brief, and its output is rejected if it invents a number.

      Edge cases in the replay

      • Duplicate ticket id: the second ticket is dropped and counted, never cooked twice.
      • 86’d item: the ticket is blocked before a station is touched.
      • Promise already in the past: the plan collapses to fire immediately.
      • Empty ticket: blocked, not crashed.
      • Twelve-item party order: the critical path and the backlog decide, not the item count.
      • No courier assigned: the plan uses the promised time plus learned bias with a wider spread.
      • HTML in a ticket note is escaped, never rendered.

      Honest limits of the evidence

      This is a simulator, not a production POS integration. It is calibrated to be plausible, not to match a specific restaurant. The comparison is paired and seeded, so the difference between policies is meaningful; the absolute minutes are illustrative.
